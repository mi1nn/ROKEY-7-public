# 카메라 기반 지진 감지 선행 기술 조사와 차별점 주장 범위 (인식 레인 초안, 2026-10-12)

> 결론 먼저. 출처 표기: [문서] [계산] [추정] [미확인]. 웹 조회로 확인한 외부 자료는 [문서]이고, 이 저장소의 코드·문서 내용은 커밋 `c79097d` 기준으로 읽었다. 이 문서는 어떤 RQ·AC·Q·D·C 도 확정하지 않는다. 모든 `[제안]` 은 확정이 아니다.

## 0. 결론

1. **같은 시스템은 아니다.** 고정 웹캠의 화면 이동을 블록 매칭으로 재고 시간 창 안의 왕복 횟수를 세는 원리는 Sony 특허(2010) 명세의 설명과 비슷하다 [문서]. 선행 기술의 코드·데이터·임계값이 공개돼 있지 않아 직접 비교는 불가능하다. 그래서 "기존 시스템보다 낫다"는 주장은 하지 않는다.
2. **포지션은 조기 경보가 아니라 지진 직후 실내 초동 대응이다.** 선행 기술은 "얼마나 센가"에 답하고 경보나 측정에서 끝난다. 이 프로젝트의 판정은 "로봇을 보낼 만한 흔들림 사건이 있었는가"에 답하고 정찰 임무 발급으로 이어진다. 다만 이 판정은 진도와 보정되어 있지 않다(3절).
3. **카메라는 간접 센서다.** 세기와 P파를 재지 못하고 조명·가림에 약하다. "기존 CCTV에 소프트웨어만 추가"는 가속도계 대비 장점이며, POSTECH·IBM 같은 카메라 선행 기술과는 공통점이다(4절).

> [!WARNING]
> 확인 범위 (2026-10-12): 2절 특허 3건의 날짜와 청구항 1은 Google Patents 페이지에서 직접 읽어 대조했다. 대조 결과 일부 내용은 청구항이 아니라 명세(설명)에 있다(2절 표에 표시). 아직 읽지 못한 것: 종속항 전체, 법적 상태(IBM). 발표·PR 근거로 쓰기 전에 공식 원문을 한 번 더 확인한다.

## 1. 이 저장소의 판정 방식 (코드 확인)

`rescue_perception.disaster_sign` 은 고정 웹캠 영상만으로(학습 모델 없이) `SiteEvent(kind="DISASTER_SIGN")` 를 만든다. 세기(진도·가속도)는 재지 않는다. 설명은 [인식 구현 문서](../implementation/implementation-perception.md) 「고정 웹캠 지진 징후」 절에 있다.

| 단계 | 하는 일 |
| --- | --- |
| 1. 격자화 | 회색조로 바꾸고 `sample_stride` 픽셀 간격으로 줄인다 |
| 2. 블록 이동량 | 블록마다 직전 프레임과 ZNCC 로 가장 잘 맞는 이동을 찾는다. 밝기·대비 변화에 점수가 변하지 않는다 |
| 3. 영상 정상 확인 | 무늬 있는 블록·매칭된 블록이 너무 적으면 UNKNOWN(판단 보류) |
| 4. 화면 전체 확인 | 이동량 중앙값과 같은 방향의 블록이 네 사분면 모두에 있어야 한다. 아니면 부분 움직임 |
| 5. 장면 확인 | 흔들리기 전 기준 장면이 보이는 블록이 너무 적으면 UNKNOWN(`SCENE_CHANGED`, `QUADRANT_COVERED`) |
| 6. 왕복 횟수 | `window_ns` 안에 방향 전환이 `shakes_min` 회 이상이고 `hold_ns` 유지되면 사건 1개 |

한계는 이미 구현 문서에 있다: 세기는 보지 않음, 자동 초점은 배율 변화를 이동처럼 보이게 함, 실제 웹캠 오탐률·처리 속도는 NOT_RUN, 시험 30개는 합성 영상이다.

카메라 지진 감지는 이미 특허 3건과 다수 논문이 있다. 상용 제품 사례는 이번 조사(웹 검색)에서 찾지 못했다 [미확인: 없다는 뜻이 아님].

## 3. 비교

| 항목 | 선행 기술 (Sony · POSTECH · IBM · LCCTV) | 이 프로젝트 |
| --- | --- | --- |
| 언제 | 지진 도착 전·진행 중 (조기 경보) | 지진 직후 (실내 초동 대응) |

| 검증 | 특허 명세, 진동대 84건과 실제 지진 3곳(LCCTV) | 합성 영상 시험 30개, 실물 오탐률 NOT_RUN |

이 프로젝트의 판정 기준(`shift_min`, `shakes_min`)은 픽셀 이동과 왕복 횟수이고 진도가 아니다. 같은 진도라도 카메라 거치 방식·거리·화각·해상도에 따라 픽셀 이동량이 달라지고, 왕복 횟수는 세기보다 진동 지속 시간과 주파수에 가깝다. 이 대리 지표가 진도와 맞는지 보정한 적은 없다 [코드·문서 확인].

## 4. 센서 차이

실제 지진 감지의 표준 센서는 가속도계다. 카메라는 화면 픽셀 이동을 보는 간접 센서다.

| 항목 | 웹캠 | 스마트폰 가속도계 | 시설용 지진가속도계측기 |
| --- | --- | --- | --- |
| 재는 양 | 화면 픽셀 이동 | 가속도 | 가속도·속도 |
| 세기 환산 | 픽셀을 실제 거리로 보정해야 함 (이 프로젝트는 하지 않음) | 가능, 다수 폰을 서버가 종합 | 직접 가능 |
| 시간 해상도 | 30 fps 이면 이론상 15 Hz 까지 [계산: 나이퀴스트] | 수십에서 수백 Hz [추정] | 보통 100 Hz 이상 [추정] |
| P파 감지 | 사실상 어려움 [추정] | 가능, 정지한 폰이 P파를 감지 ([Google Research](https://www.research.google/blog/android-earthquake-alerts-a-global-system-for-early-warning/)) | 가능 [추정] |
| 추가 하드웨어 | 불필요 (기존 CCTV 에 소프트웨어만 추가) | 불필요 | 필요 |
| 환경 약점 | 어두움, 가림, 자동 초점·노출, 렌즈 왜곡 | 사람이 들고 움직이면 잡음 | 설치·유지 비용, 고장 |
| 사례 | 위 선행 기술 | Android Earthquake Alerts: 98개국(2023 말), 첫 규모 추정 오차 중앙값 0.50에서 0.25로 개선 [문서] | [지진·화산재해대책법](https://m.go.seoul.co.kr/news/2017/04/06/20170406014012)상 주요 공공시설 814곳 설치 의무, 2016년 감사 기준 231곳 미설치 [문서] |

## 5. 차별점 주장 범위 [제안]

선행 기술과는 직접 비교할 수 없으므로 증거 수준이 다른 네 가지 주장으로 나눠 말한다. 아래 "입증하려면 필요한 것" 은 모두 실시하지 않았다(NOT_RUN).

| 주장 종류 | 말할 수 있는 것 | 입증하려면 필요한 것 (미실시) | 현재 상태 |
| --- | --- | --- | --- |
| 1. 능력 차이 | 감지 결과가 정찰 임무 발급으로 이어진다. "더 낫다"가 아니라 "기능이 더 있다" | 흔들림 시작부터 임무 발급까지 걸린 시간, 중복 출동 0건 | 계약·임무 조정 코드 있음, 실기 NOT_RUN |
| 2. 설계 근거 (이 프로젝트 안의 비교) | 사분면 확인·기준 장면 비교·판단 보류가 각각 오탐을 줄인다. 선행 기술과의 비교가 아님 | 같은 녹화에서 부품을 하나씩 끈 버전과 상황별 오탐 건수 비교 | 사분면 요구는 정책 값으로 끌 수 없음, NOT_RUN |
| 3. 단순 방법 대비 | 프레임 차분·전역 광학 흐름 같은 흔한 단순 방법보다 오탐이 적다. 기준선을 직접 구현하므로 증거 수준은 낮다 | 튜닝 녹화에서 같은 민감도로 맞춘 뒤 새 녹화에서 오탐 비교 | 기준선 미구현, NOT_RUN |
| 4. 한계 (먼저 밝힌다) | 선행 기술과 직접 비교하지 못했다. 세기·P파·다중 카메라·실제 지진 검증은 없다. 흔들기는 손으로 흔든 것이다 | 해당 없음 | 확인됨 |

쓰지 않는 문장: "Sony(또는 POSTECH·IBM)보다 낫다", "지진 감지 성능을 검증했다", "진도를 추정한다". "새로운 지진 감지 기술" 도 쓰지 않는다.

### AI 모델 도입 [제안: 지금은 하지 않음]

정확도가 낮다는 측정이 없다. 실제 지진 영상이 부족해 결국 손으로 흔든 영상으로 학습하게 되고, 이 저장소의 인형 탐지 데이터셋이 영상 하나를 무작위로 나눠 평가 43개 중 39개가 학습과 사실상 같았던 선례가 있다([구현 문서](../implementation/implementation-perception.md)). POSTECH·IBM 이 이미 딥러닝을 쓰는 축에서 경쟁하게 되고, 일정(10-16)도 빠듯하다. 상황별 오탐률을 먼저 재고, 임계값으로 해결되지 않는 패턴이 나올 때만 `probe.csv` 특징을 입력으로 하는 작은 분류기를 검토한다.

## 6. 현재 결정 (2026-10-12) [제안]

추가 구현과 측정은 하지 않는다. 이 문서는 조사와 고민의 기록으로만 남긴다. 측정하지 않았으므로 다음은 확인되지 않았다(NOT_RUN): 상황별 오탐률, 특징이 적은 웹캠 장면에서의 동작, 처리 속도(`proc_ms`), 흔들림 시작부터 임무 발급까지의 시간.

나중에 측정을 다시 시작할 때 알아야 할 코드상 사실만 남긴다(코드 확인, 2026-10-12).

- `tools/webcam_quake_probe.py` 의 `--record` 는 덧그린 대시보드 화면(`view.mp4`)만 저장하고, `--video` 재생은 시각을 `프레임 번호 / fps` 로 다시 만들며 라벨을 재생 중 키 입력으로 정한다. 같은 영상을 여러 방식에 돌려 비교하려면 원본 프레임·프레임별 시각·라벨 저장이 먼저 필요하다.
- 현재 정책 값(장면 일치 0.6, 보임 30%)은 2026-10-10 녹화 분석에서 골랐다고 구현 문서에 적혀 있다. 같은 녹화로 평가하면 낙관적이다.
- 사분면 요구(`_whole_view` 의 `len(agreeing) == 4`)는 정책 값으로 끌 수 없다. 기준 장면 확인은 `scene_match_min=-1`, 판단 보류는 `valid_ratio_min` 을 작게 해 근사로 끌 수 있다. 끄는 방법(정책 필드 또는 판정기 생성자 옵션)은 [미결정]이다.
