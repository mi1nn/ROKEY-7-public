[일정과 담당](schedule.md)의 날짜·관문을 **무엇이 어느 릴리즈에 들어가고 무엇이 빠지는지**로 다시 자른 문서다. 날짜·담당·칸 일정은 [schedule.md](schedule.md)와 [일정표 CSV](schedule-timeline.csv)가 기준이고 여기서 다시 적지 않는다. 시험 ID 와 증거 층위(E1 ~ E4)는 [시험과 작업 분담](acceptance-plan.md) A-02 를 따른다.

시나리오는 [BRD Part I](../requirements/brd-part1-v0.1.md)(지진, Phase 1)에 2026-10-09 고정 웹캠 1대 결정과 2026-10-10 Q-12 결정(AMR1 자동 정찰, AMR2 운영자 승인·구간 ‘계속’)을 더한 흐름이다. 같은 흐름을 [BRD v0.2](../requirements/brd-v0.2.md)(초안) 2장 그림이 그린다. 아래 "1 ~ 7 단계" 는 그 흐름을 번호로 부른 것이고, 오른쪽 칸은 Part I 번호다. Part I 에 없는 내용은 v0.2 번호를 적는다.

## 1. 릴리즈 단위

- 릴리즈는 `main` 의 태그다(`v0.1`, `v0.2`, `v0.3`, `v1.0-rc`, `v1.0`). 관문을 통과한 날 저녁에 작전이 증거 링크를 모아 요청하고, 사용자가 태그를 민다.
- 태그마다 아래 3절 표의 "증거" 칸을 채운 뒤에만 태그한다. 증거가 `NOT_RUN` 이면 태그하지 않고 날짜를 미룬다. 태그를 위해 합격 조건을 낮추지 않는다(acceptance-plan A-01).
- `v1.0-rc` = 기능 동결([schedule.md](schedule.md) 10-14 저녁). 이후 `main` 에는 수정 PR 만 받는다. 새 기능은 발표 뒤 목록(5절)으로 보낸다.
- **릴리즈마다 빼는 것을 먼저 적는다.** 그래야 날짜별로 "안 되는 것" 을 솔직하게 말할 수 있다.
