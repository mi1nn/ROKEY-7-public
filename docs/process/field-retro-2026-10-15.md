# 10-15 실습에서 어려웠던 점

10-15 오후 실습(로봇 담당 PC 한 대 + 운영 PC + Discovery 전용 PC)을 돌린 사람 입장에서, 무엇이 어려웠고 왜 어려웠는지 정리한다. 무엇이 일어났는지는 [실습 기록](../evidence/field-2026-10-15-run1015.md)과 [운영 PC 기록](../evidence/field-2026-10-15-operations-host.md)에 있고, 거기서 뽑은 원리는 [레슨런](lessons-learned.md) LL-12 ~ LL-17 이다. 이 문서는 그 둘을 다시 적지 않고 「다음에 같은 고생을 하지 않으려면」에 맞춘다.

## 1. 왜 막혔는지 화면에 안 나왔다

- **무엇이 어려웠나.** TB-6 출발 승인(`task_arm`)이 `STOP_OR_READINESS_NOT_READY` 로 두 번 거절됐다. 한 번은 카메라 토픽, 한 번은 깊이 카메라 때문이었는데, 답에는 이유 코드 하나뿐이었다. 사람이 토픽마다 `ros2 topic hz` 를 돌려 하나씩 찾았다. Nav2 가 반만 켜졌을 때는 오히려 「준비됨」이 나와 재난 선포까지 가 버렸다.
- **왜.** 준비 판정이 「있다」만 보고 「동작한다」를 보지 않았고, 거절할 때 빠진 신호를 남기지 않았다.
- **지금.** #340 은 Nav2 lifecycle 이 active 일 때만 준비로 본다. #342 는 거절할 때 `TASK_ARM refused <코드> missing=[...] sources=[...]` 를 로그와 서비스 답에 남긴다. #343 은 Nav2 가 준비 안 된 이유를 로그에 남긴다.
- **다음 실기에서 볼 것.** 거절되면 이 줄 하나로 원인이 보이는지.

## 2. 망이 자꾸 흔들렸다

- **무엇이 어려웠나.** ping 이 1초 넘게 튀고 TB-5 가 망에서 거의 떨어졌다. Discovery 전용 PC 가 재부팅된 뒤 서버가 30분 동안 꺼져 있었는데, 그 사이 「로봇이 안 보인다」의 원인을 로봇 쪽에서 찾았다. 다른 팀 PC 가 같은 도메인에서 `/robot6/map` 을 내 우리 지도처럼 보였다.
- **왜.**
  - 로봇 Pi 무선 절전은 재부팅하면 다시 켜지는데, 「켤 때마다 끄기」를 빠뜨렸다.
  - 큰 RGB 영상은 받는 프로세스마다 Wi-Fi 로 한 번씩 더 온다.
  - Discovery 서버는 터미널에서 띄운 프로세스라 재부팅 뒤 다시 뜨지 않았다.
  - 같은 도메인과 같은 Discovery 서버를 쓰면 다른 팀 노드도 우리 그래프에 들어온다.
- **지금.**
  - 실습 안내에 Pi 무선 절전, Discovery 서버 먼저 확인, 지도 발행 노드 확인 줄을 넣었다(#337·#339).
  - 준비 점검 카메라를 가벼운 camera_info 로 바꿨다(#342).
- **남은 것(재범 결정).**
  - Discovery 서버 사용자 서비스 등록
  - 로봇망 안 시간 서버. 운영 PC 시계 지연이 7.5 s 까지 났다.
  - 운영 PC Wi-Fi 절전
  - 다른 팀과 도메인 나누기
  - 깊이 영상 준비 점검을 같은 PC 안 결과로 바꿀지

## 3. 로봇 하드웨어가 따로따로 멈췄다

- **무엇이 어려웠나.** 증상은 모두 「명령이 안 먹는다」 하나였지만, 원인이 매번 달랐다.
  - Pi turtlebot4 서비스를 다시 시작하자 Create3 연결이 돌아오지 않아 언도킹이 멈췄다(두 로봇).
  - TB-6 라이다가 두 번 멈췄다.
  - TB-6 깊이 카메라만 멈추고 RGB 는 정상이었다.
- **왜.** 원인은 아직 모른다 [미확인]. 다만 복구 방법은 찾았다: Create3 재시작, Pi 에서 turtlebot4 서비스 재시작, 카메라 `stop_camera` → `start_camera`.
- **지금.** 실습 안내 2단계에 증상별 확인 줄과 복구 순서를 넣었다(#339·#345). 로봇 쪽 재시작은 재범 승인 뒤에 한다.
- **남은 것.** 라이다와 깊이 카메라가 멈추는 원인.

## 4. 설정을 손으로 고쳐서 PC 마다 맞췄다

- **무엇이 어려웠나.** 실기용 배포 프로파일이 따로 없어, 예시 파일을 PC 마다 고쳤다(network 블록 → namespace 를 sed 로). 그 뒤 두 PC 의 sha256 을 맞췄다. TB-5 출발값도 현장 파일에 먼저 손으로 넣고 저장소에 따로 올렸다(#334). 저장소 시험 22개가 「아직 값이 없다」를 전제로 하고 있어 함께 고쳐야 했다.
- **왜.** 현장 값(주소, namespace, 측정값)을 저장소 밖에 두는 규칙은 맞다. 하지만 그 값을 만드는 절차가 없었다.
- **지금.** #348 은 저장소 예시에서 명령 하나로 프로파일을 만든다. 같은 입력이면 어느 PC 에서나 sha256 이 같다.
- **다음 실기에서 볼 것.** 두 PC 에서 만든 파일의 sha256 이 같은지. 로봇 담당 PC 의 빌드 커밋은 오늘 기록에 없었으니 회차 폴더에 `HEAD.txt` 로 남긴다.

## 5. 띄우는 순서에 따라 결과가 달라졌다

- **무엇이 어려웠나.**
  - 실행기를 조정기보다 늦게 띄우면 실행기마다 `CLOCK_UNCERTAIN` 이 나서 손으로 `refresh_state` 를 불렀다.
  - 지도 고정 노드를 다시 띄우자 새 출발 자세가 생겨 조정기가 `START_POSE_CONFLICT` 로 거절했다.
  - 백그라운드로 띄운 slam_toolbox 가 inactive 에 머물렀다.
  - 서 있는 TB-6 에서 위치가 나오지 않아 출발 자세가 안 잡혔다.
- **왜.**
  - 조정기는 상태가 바뀔 때만 SystemState 를 냈다.
  - 출발 자세는 조정기 프로세스 하나에 한 번만 받는다(설계).
  - lifecycle 전환 이벤트를 놓칠 수 있다 [추정].
  - slam_toolbox 기본값은 움직인 스캔만 처리한다.
- **지금.**
  - #349: 상태를 주기적으로 다시 낸다.
  - #341: 서 있어도 처리하는 SLAM 설정. 켜지지 않으면 로그를 남기고 한 번만 다시 켠다.
  - 실습 안내 8단계: 지도 고정 노드를 다시 띄우면 조정기도 다시 띄운다(#339).

## 6. 한 번 실패로 임무가 끝났다

- **무엇이 어려웠나.** 재난 선포 2초 뒤 「생존자 없음」으로 끝났다. TB-6 은 한 걸음도 움직이지 않았다. 처음에는 탐색이 끝난 것처럼 보여 원인을 늦게 찾았다.
- **왜.** Nav2 가 거절한 첫 목표를 「가 봤음」으로 막았고, 남은 후보가 없어 몇 초 만에 탐색을 끝냈다.
- **지금.** #338 은 출발하지 못한 목표를 다시 고르고, 그동안 `SCOUT_GOAL_NOT_STARTED` 를 보인다.
- **남은 것(재범 결정).** Nav2 가 끝까지 꺼져 있으면 탐색 시간 한도(600 s) 뒤 지금처럼 「생존자 없음」으로 끝난다. 한 번도 움직이지 않았으면 이 결론을 내지 않게 할지 정한다.

## 7. 웹이 없으면 볼 수단이 없었다

- **무엇이 어려웠나.** 임무 상태, 막힌 이유, 고정 단계, 대상 위치가 관제 웹에만 있었다. 웹이 이상하면 터미널 로그를 PC 마다 뒤져야 했다. 명령도 웹 버튼이나 손으로 짠 `curl` 뿐이었다.
- **지금(웹 없는 트랙).**
  - #344: 명령 도구 `operator_command.py`, 상태 한 줄 `status_watch.py`
  - #346: 두 로봇 RViz 설정과 실습 안내 「웹 없이 하기」
  - #351: 인형·출구 RViz 마커
- **다음 실기에서 볼 것.** RViz 화면에서 지도, TB-5 위치, 마커가 제자리에 나오는지.

## 8. 누가 무엇을 하는지 엇갈렸다

- **무엇이 어려웠나.**
  - 같은 작업(TB-5 추정 위치 표시)을 두 자리에 맡기는 지시가 몇 분 사이에 엇갈렸다. 그중 한 지시는 시각을 잘못 적어 순서가 뒤집혀 보였다.
  - 현장을 맡은 자리가 PR 을 하지 않기로 정해지면서 맡겼던 일을 다시 나눴다.
  - 여러 자리가 같은 실습 안내를 동시에 고쳐 충돌을 피하느라 나눠 올렸다.
  - 검증 요청이 남은 PR 이 머지되어 고칠 것을 새 PR 로 옮겼다.
- **왜.** 자리마다 맡는 일(현장 실행, 웹을 띄우는 자리, 웹을 만드는 자리, 머지)이 문서로 고정돼 있지 않았다.
- **다음에.**
  - 일을 맡길 때 「누가 만들고, 누가 검증하고, 누가 머지하는지」를 한 메시지에 같이 적는다.
  - 지시 시각은 실제 시각으로 적는다.
  - 같은 파일을 여러 자리가 고칠 때는 먼저 올라온 PR 을 기준으로 이어 고친다(`git merge-tree` 로 충돌 확인).

## 다음 실기 전 체크

1. 모든 PC 를 같은 main 으로 받고 다시 빌드한다(#340 은 새 필수 파라미터). 회차 폴더에 `HEAD.txt` 를 남긴다.
2. 프로파일을 `make_field_profile.py` 로 새 폴더에 만들고, PC 마다 sha256 을 대조한다.
3. 로봇 Pi 두 대의 무선 절전을 끈다. 언도킹 뒤 `dock_status`, RGB `camera_info`, 깊이 `camera_info` 가 오는지 본다.
4. Discovery 서버가 떠 있는지, `/robot6/map` 발행 노드가 `slam_toolbox` 하나인지 본다.
5. 출구 QR 문자열을 확인한다(인식 노드 인자).
6. 실행기 로그에서 `NAV2_LIFECYCLE ... active` 가 나오는지 본다. 거절되면 `TASK_ARM refused ... missing=[...]` 를 기록한다.
